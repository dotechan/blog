# Iceberg article kit

社内ブログへ HTML で投稿するときの、色と部品を固定するテンプレートです。配色は [iceberg.vim](https://github.com/cocopon/iceberg.vim) のダーク／ライトを基にしています。

生成 AI には記事の中身と、用意した class の選択だけを任せます。CSS はその場で書かせません。

## ファイル

| ファイル | 役割 |
| --- | --- |
| [iceberg.css](iceberg.css) | 配色と部品のスタイル。`.ib-article` の中だけに閉じる |
| [template.html](template.html) | 使える部品の一覧。ブラウザで開いて見本になる |
| [prompt.md](prompt.md) | HTML 化を頼むときのプロンプト |
| [build.mjs](build.mjs) | 断片の検証、style 埋め込み版、インライン版の生成 |
| [samples/sample.html](samples/sample.html) | 既存記事「カラースキームであるICEBERGを使ってみた」を当てはめた見本 |

## 使い方

1. 原稿と [prompt.md](prompt.md) を AI に渡し、`<article class="ib-article">` だけの HTML を出させる。部品の構造は [template.html](template.html) を一緒に渡すと安定する。
2. 出力を HTML ファイルとして保存する。
3. 検証して投稿用ファイルを作る。

```bash
cd iceberg-article-kit
npm install
npm run build
# または
node build.mjs path/to/fragment.html
```

`dist/` に次の 3 ファイルが出ます。

- `*.style.html` … `<style>` に CSS を埋め込んだ版。OS のダーク／ライトに追従する。`<style>` を置ける CMS 向け。
- `*.inline.light.html` / `*.inline.dark.html` … 色を要素の `style` 属性に展開した版。`<style>` が消される CMS 向け。投稿するのは中の `article` 要素。

class の追加、`style` 属性、`<svg>`、許可していない要素があると `build.mjs` はエラーで止まり、理由を列挙します。

## 配色

トークンは `.ib-article` に置き、CMS 側の CSS とぶつからないように class は `ib-` で始めます。記事自身が背景色を持つので、白い画面の上でもダークモードが透けません。

枠線、面、差分の背景は iceberg の色をそのまま使います。文字として使う次の色は、背景とのコントラストが WCAG AA（4.5:1）に届かなかったため、同じ色相のまま濃さを変えています。

| 用途 | モード | iceberg の色 | 文字に使う色 |
| --- | --- | --- | --- |
| 補助テキスト | ライト | `#8389a3`（2.85:1） | `#5c6072` |
| 補助テキスト | ダーク | `#6b7089`（3.63:1） | `#9094a7` |
| 文字列・情報 | ライト | `#3f83a6` | `#326985` |
| 推奨 | ライト | `#668e3d` | `#4d6b2e` |
| タイトル・注意 | ライト | `#c57339` | `#8f5329` |
| 危険 | ライト | `#cc517a` | `#a34162` |
| 定数 | ライト | `#7759b4` | `#7053a9` |

ダークの青、緑、橙、赤、紫は元の色のまま基準を満たします。コードの色分けは iceberg の対応に合わせ、予約語・関数・型は青、文字列は水色、数値は紫、コメントは補助テキストです。

## インライン版で失われるもの

`<style>` を消せない CMS では、次は使えません。

- OS 設定に追従するダーク／ライトの切替。ビルド時にどちらかを選ぶ。画面が白ならライト。
- `:hover` と `:focus-visible`。リンクは下線だけで識別できる。
- `::selection`。

SVG はどちらの版でも使いません。流れ図は文字の矢印です。

## アプローチの比較

### A. 毎回 AI に HTML と CSS を書かせる

準備はいりません。その代わり、色も余白も記事のたびに変わり、CMS が SVG や `<style>` を消す制約を毎回説明する必要があります。見た目の再現性がなく、書き手の色も残りません。

### B. テンプレートと CSS を固定し、AI には当てはめだけさせる（このキット）

見た目は CSS が決めるので、記事ごとの色の揺れが止まります。AI の自由度は部品の選択だけです。プロンプトに CSS 全文を載せなくて済みます。

残る揺れは、存在しない class を書く、本文を要約しすぎる、コードの色分けを外す、といったモデル側の失敗です。class とタグの検査は `build.mjs` が受け持ちます。コードの色分けはモデルが span を付けるので、ここだけは機械的ではありません。部品を増やすたびに CSS、カタログ、プロンプト、許可リストを揃えて直す必要があります。

### C. AI は Markdown を書き、HTML 化は変換ツールが行う

同じ原稿なら同じ HTML になります。コードの色分けもハイライタに任せられます。再現性は B より高いです。

コールアウトやカードを表すには、Markdown の拡張記法と変換ルールが別途要ります。最初の手間は B より大きいです。このキットの class と CSS は変換結果の当て先としてそのまま使えます。

### D. CMS 標準の Markdown だけで書く

制約を気にせず、テンプレートの保守もありません。iceberg の色は出ません。

### 判断

最初は B で部品（許可する class）を固めるのがよいです。CSS は変換ツールに依存していないので、モデルの揺れが問題になった時点で「AI は Markdown、HTML はスクリプト」という C へ移せます。D は色を諦めるときの下限です。A は再現したい見た目があるなら使わない方がよいです。
